## The process that's been working

Each module 01–07 was generated by spawning a single `general-purpose`
Agent per module (via the `Agent` tool) with a long, detailed prompt that:

1. Points it at `MASTER_LEARNING_PLAN.md` (the rules) and `RUNNING_PROJECT.md` (the QuestLog spec).
2. Points it at the *previous* module's finished `project/questlog/` as the exact starting codebase to copy forward and extend (never regenerate from scratch).
3. Points it at 1–2 prior modules' `lessons/00-setup.md` files as a tone/depth calibration example.
4. Spells out that specific module's curriculum from the master plan, with a suggested lesson-file breakdown.
5. Explicitly requires real web research (Rule 7) for anything version/library-specific, and names the specific things to verify.
6. Requires a self-audit against Rules 1/5/6/7/8/9 before reporting done.
7. Requires appending new terms to `GLOSSARY.md` **in correct alphabetical position** (the file is large — ~1700 lines — so this means finding the right spot via Grep/Read, not just appending at the end).
8. Explicitly forbids touching any other module's folder or any root file besides `GLOSSARY.md`.
9. Asks for a final report under ~450 words: files created, versions verified with dates, what was live-tested vs. hand-verified, and the self-audit result.

**After every agent call finishes, verify on disk before trusting the
report** — this repo has already had one case (Module 06) where the
agent's self-report and the actual on-disk state disagreed after a
connection failure. See below. A cheap verification pattern:
```bash
find module-XX-name -type f | sort          # does the file list look complete/sane?
find module-XX-name -type d -name node_modules -o -type d -name __pycache__ -o -type d -name ".venv*"   # any stray build artifacts to delete?
grep -c "Module XX" GLOSSARY.md              # did glossary entries actually land?
```

## Known issues already hit (so you don't repeat them)

1. **Long agent calls can get cut off mid-response** ("Connection closed
   mid-response" / API errors). When this happens, **do not restart from
   scratch** — use `SendMessage` to the same `agentId` (given in the failed
   call's result) telling it to re-check the current on-disk state of its
   module folder and continue from wherever it actually left off, then
   re-run its own self-audit and give a fresh final report. This worked
   cleanly for both Module 05 and Module 07's interruptions.
2. **A session-wide usage limit can be hit**, which fails *every* agent
   call (not just one) until it resets — the error explicitly states a
   reset time. If you hit this, there's no point retrying immediately;
   either wait, or fall back to writing lesson/exercise files directly
   yourself with `Write`/`Edit` (slower, but works — this is exactly how
   Module 06 got finished after its second connection failure coincided
   with a session limit).
3. **Module 06 specifically needed manual repair** after its interrupted
   agent run: it had left a stray `.venv-test/` folder (a full installed
   virtualenv, deleted), a `requirements.txt` missing `sqlalchemy`/
   `alembic`/`asyncpg` despite the code importing them, and two `README.md`
   files still describing themselves as "Module 05." All of Module 06's
   `lessons/`, `exercises/`, `CHECKLIST.md`, `README.md`, and
   `project/BRIEF.md` were then written by hand (not via agent) to finish
   it. **Lesson: always verify a module's file list and skim its READMEs
   for stale "Module NN" references after any interrupted run, before
   trusting it's done.**
4. **Stray build artifacts.** Agents that actually run/test code (installing
   a venv, running `npm install`, etc.) sometimes forget to delete the
   result. Always grep for `node_modules`, `__pycache__`, `.venv*` inside a
   newly generated module and delete any that snuck in — they don't belong
   in the course repo.
5. **`Read`/`Bash` on files matching certain patterns (e.g. `.env*`) can be
   permission-denied** by the harness even for legitimate inspection — this
   is expected sandboxing, not a bug; work around it by reading adjacent
   non-sensitive files (`.gitignore`, `README.md`) instead.
