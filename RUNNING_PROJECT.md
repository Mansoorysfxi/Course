# The Running Project: QuestLog

Per `MASTER_LEARNING_PLAN.md` Section 5 ("keep a consistent running project
... so the learner sees one app evolve"), this course builds one
continuous application across most modules, alongside smaller standalone
exercises. This file is the single source of truth for what that project is
so every module stays consistent — any session generating a new module
must read this first.

## The concept

**QuestLog** — a personal task tracker with light RPG framing (a nod to the
learner's game-dev background): tasks are called "quests," completing a
task is "completing a quest," a group of related tasks is a "quest line."
This is a deliberately simple domain (nothing about the business logic
should ever be the hard part) so every module's added complexity is about
the *technology*, not about understanding a complicated domain.

## Fixed technology decisions (so later modules don't re-litigate earlier ones)

These are chosen once, here, verified via web research when the module that
introduces them is generated, and then treated as fixed for the rest of the
course:

- **Frontend:** React + TypeScript, built with Vite; Tailwind CSS for styling; React Router for routing. Next.js is taught conceptually (SSR/SSG/CSR) in Module 04 but QuestLog itself stays a Vite SPA — introducing a second frontend build system mid-course would add incidental complexity Rule 1 doesn't require.
- **Backend:** Python + FastAPI, Pydantic v2 for models.
- **Database:** PostgreSQL, accessed via SQLAlchemy 2.0 (async) + Alembic for migrations. Redis introduced in Module 06 conceptually, used for real starting Module 10 (caching + Docker Compose multi-service example).
- **Auth:** JWT-based, `passlib`/`bcrypt` for password hashing (exact package verified when Module 07 is generated, since this space changes).
- **Containers/Deploy:** Docker + docker-compose; concrete cloud target for Module 11 chosen (with research) when that module is generated, with alternatives mentioned per the master plan.
- **CI/CD and cloud deploy target (decided when Module 11 was generated):** **GitHub Actions** for CI/CD (free, no ambiguity, verified current syntax/action versions as of August 2026) and **Render** as the concrete container-platform deploy target — chosen over Fly.io and Railway specifically because both discontinued their own genuine free tiers by 2026 (verified via live research at generation time; Fly.io now offers only a 2-hour/7-day trial for new signups, Railway a one-time $5 credit then $1/month), and over configuring raw AWS/GCP compute by hand because that would require its own multi-lesson module of IAM/VPC/networking setup this module's actual subject (CI/CD) doesn't need. Render's free tier — Docker-image-backed web services, managed Postgres, a Redis-compatible Key Value cache, and fully automatic Let's Encrypt/Google Trust Services TLS on both its own subdomains and custom domains — covers every piece this module's capstone needs at zero cost. This is a deliberately different, higher-management tier than Module 09's raw Hetzner VPS (never re-litigating that module's own choice — the VPS lessons/exercises are unchanged), chosen specifically so Module 11's automatic HTTPS and one-file (`render.yaml`) deploy configuration read as a real, felt contrast to Module 09's manual, HTTP-only deploy. QuestLog's backend/frontend images (Module 10's own, unmodified Dockerfiles) are pushed to GitHub Container Registry by a GitHub Actions pipeline and deployed to Render via its Deploy Hook mechanism, pinned to an exact commit SHA. See `module-11-cicd-cloud-production/lessons/04-cloud-fundamentals-and-your-chosen-platform.md` for the full research and reasoning, and `lessons/08-deploying-questlog-with-ci-cd.md` for the complete, applied walkthrough.
- **AI:** Anthropic API (Claude) as the primary LLM API taught in Modules 13–15, per the master plan.
- **QuestLog's first AI feature's model (decided when Module 13 was generated):** **`claude-haiku-4-5`**, Anthropic's cheapest and fastest current model as of Module 13's generation (verified: $1.00/million input tokens, $5.00/million output tokens), for the quest-breakdown assistant endpoint (`POST /api/quests/{quest_id}/suggest-breakdown`) — chosen because suggesting 2-4 short sub-quest titles doesn't need a larger model's deeper reasoning, per Module 13, Lesson 05's own "pick the cheapest model that does the job" cost-management principle. Set via a new, optional `AI_MODEL` setting (`backend/app/config.py`, defaulting to this value) so a later module can swap it without a code change. See `module-13-building-with-llm-apis/lessons/00-setup.md` and `lessons/07-building-questlogs-ai-assistant-backend.md` for the full reasoning.
- **Redis's concrete use case (decided when Module 10 was generated):** a Redis-backed cache for `GET /api/quests`'s *unfiltered* quest list only (the call QuestLog's own Quest Board page makes on every load) — a 30-second TTL plus active invalidation (a `redis.delete` call) on every `create`/`update`/`delete` quest route, keyed per-owner so two users never share a cached answer; any filtered call (`?done=`, `?priority=`, `?quest_line=`) deliberately bypasses the cache entirely and always hits Postgres, keeping this module's scope to "a real, working example of the concept," not a general-purpose caching layer. Implemented via `redis.asyncio` (the `redis` PyPI package, not the deprecated standalone `aioredis`), wired in as a FastAPI dependency (`RedisClient`, mirroring the existing `DbSession`) entirely inside `app/routers/quests.py` — `app/repository.py` is untouched. See `module-10-docker-and-containers/lessons/06-docker-compose-multi-service-apps.md` and `lessons/07-containerizing-questlogs-backend.md` for the full explanation.
- **QuestLog's embedding-model decision (decided when Module 14 was generated):** the free, local `sentence-transformers` model (`all-MiniLM-L6-v2`, 384 dimensions), the exact model already verified in Module 12, powers "chat with your quest notes"' chunk-to-vector step (`backend/app/embeddings.py`), rather than a paid embeddings API. Anthropic itself has no embeddings model and officially recommends Voyage AI as its preferred third-party partner (verified August 2026: `voyage-4-lite` at $0.02/million tokens, 200 million free tokens per new account) — a real, credible, cheap alternative this course chose not to take, specifically because it would require a *second* API key/account beyond the `ANTHROPIC_API_KEY` already required since Module 13, for a job the free local model already does perfectly well at this app's actual scale. The accepted trade-off, stated honestly: `sentence-transformers` pulls in `torch` as a transitive dependency, meaningfully growing the backend's install size and Docker image; `app/embeddings.py` loads the model lazily (on the first real embedding call, not at process startup or even at plain import time) so that cost is paid at most once per running server process, and never at all by the backend's own test suite, which mocks the embedding functions directly. See `module-14-rag/lessons/00-setup.md` and `lessons/03-embeddings-for-search.md` for the full reasoning.
- **pgvector and the Docker image it required (decided when Module 14 was generated):** each note chunk's embedding is stored in a real Postgres `vector(384)` column via the `pgvector` extension (Postgres extension version 0.8.6; the `pgvector` PyPI package, `pgvector-python`, at 0.5.0 for the SQLAlchemy 2.0 integration — both verified August 2026). Because no official Alpine-based pgvector image exists for Postgres 18 as of that date (Alpine's own community `postgresql-pgvector` package lives only in its unstable `edge` branch, unsuitable for a course's reference config), `docker-compose.yml`'s `postgres` service image changes from Module 10's `postgres:18-alpine` to the extension's own official `pgvector/pgvector:pg18` image — Debian-based and larger than Alpine, a small, honest trade-off accepted for a stable, pre-built pgvector installation instead of an unofficial Alpine package; nothing else about that service changes. Similarity search uses pgvector's cosine-distance operator (`<=>`) via a real HNSW index, built by hand first with no framework, per the master plan (LangChain/LlamaIndex are discussed only afterward, honestly, in `lessons/07-rag-frameworks-honestly.md`). See `module-14-rag/lessons/00-setup.md` and `lessons/04-vector-databases-and-pgvector.md` for the full research and reasoning.
- **QuestLog's agent tool set, guardrails, and memory scope (decided when Module 15 was generated):** the final capstone's agent (`backend/app/agent.py`, `POST /api/agent/chat`) exposes exactly six tools — `list_quests`, `create_quest`, `update_quest`, `complete_quest`, `search_quest_notes`, and `suggest_quest_breakdown` — every one a thin wrapper around code Modules 06, 13, and 14 already wrote and tested (`app/repository.py`'s CRUD functions, and Module 14's `embed_text`/`find_similar_chunks` reused directly for retrieval, never re-implemented). There is deliberately **no `delete_quest` tool**: QuestLog's own `delete_quest` is a real, permanent operation with no undo, and the cheapest honest guardrail is not exposing that capability to the agent at all — a player who wants to delete a quest still uses QuestLog's existing UI. Every tool that touches a specific quest is scoped through the same ownership check (`app/repository.py`'s `get_quest(session, quest_id, owner_id=...)`) every route in this app has used since Module 07, and `create_quest`/`update_quest` validate the model's own tool arguments through the exact same `QuestCreate`/`QuestUpdate` Pydantic models the real HTTP routes already validate request bodies against. The loop itself is capped at `MAX_AGENT_ITERATIONS = 8` per conversational turn (the same real, enforced-in-code pattern Module 13's own `MAX_TOOL_ITERATIONS` first established, sized larger here because this agent's own job is open-ended rather than one narrow feature), and every turn ends with a `usage` event reporting its own iteration and tool-call counts, so cost is a visible number in the UI, never a hidden one. **Memory scope, stated plainly:** short-term only, held entirely in the frontend's own React state (`AgentChatPanel.tsx`'s `messages`) and resent in full on every request — nothing about a conversation persists on the backend between requests, across a page reload, or across a browser session, and even one turn's own internal tool-calling scratch work is never resent on a later turn, only its finished, visible answer text. This module also ships one small, clearly-scoped, **read-only** MCP server (`backend/app/mcp_server.py`, run standalone via `python -m app.mcp_server`, never part of the production FastAPI app or its `requirements.txt`) exposing QuestLog's own `list_quests`/`find_similar_chunks` to any MCP-compliant client, scoped to the app's own seeded demo account rather than solving per-connection authentication for a teaching artifact — a real, honest, deliberately bounded tie-back to Lesson 05's own MCP teaching material, not a second production surface. See `module-15-agents-and-modern-ai-workflows/lessons/08-agent-safety-guardrails-and-evals.md` and `lessons/10-building-questlogs-agent-backend.md` for the full reasoning behind every decision above.

## Repo location for the running project's actual code

Each module that touches QuestLog includes the growing codebase inside that
module's own `project/` folder (e.g.
`module-04-react/project/questlog/`), and each new module's starter code
is a copy of the *previous* module's finished reference solution — so a
learner who's behind can always pick up from a working prior state. This
mirrors exactly how you'd branch/continue a real evolving codebase, which
the learner already practiced in Module 00.
